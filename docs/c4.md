# Arquitetura C4 --- Cache de veículos via CDC

## Visão geral

Este documento descreve a arquitetura da solução de cache de veículos
alimentada por **Change Data Capture (CDC)**, utilizando PostgreSQL,
Debezium, Kafka, um Worker em .NET 10 e Valkey.

A documentação está organizada em três níveis de abstração, seguindo o
modelo C4:

1.  **Context:** apresenta os atores, sistemas externos e o fluxo de
    dados da solução.
2.  **Container:** detalha os serviços, suas responsabilidades e a
    infraestrutura executada no Kubernetes.
3.  **Component:** apresenta a organização interna do Worker e o
    pipeline de processamento dos eventos.

Os diagramas utilizam Mermaid (`flowchart`) para proporcionar maior
controle visual, legibilidade e consistência entre os níveis
arquiteturais.

## Escopo e fidelidade

Os diagramas representam a infraestrutura definida pelos manifests
Kubernetes e pelo `justfile`, considerando principalmente o ambiente
criado pelo comando `just e2e`.

-   **Ambiente E2E:** cluster kind `fleet`, namespace `fleet`.
-   **Execução normal:** recursos provisionados por `just up`.
-   **Recursos exclusivos do E2E:** elementos identificados
    explicitamente nos diagramas e nas descrições.
-   **Estado de validação:** a representação do Container reflete os
    manifests e o `justfile`, ainda não executados para validação
    integral. Consultar as pendências registradas no ADR.

Caso a implementação, os manifests ou o fluxo de execução sejam
alterados, este documento deverá ser atualizado para preservar a
correspondência entre arquitetura e código.

# 1. Context

## 1.1. Visão arquitetural

A solução mantém uma projeção do estado atual dos veículos em Valkey,
alimentada exclusivamente por eventos de CDC originados no PostgreSQL.

O Worker não consulta o banco operacional. Ele consome os eventos
publicados no Kafka, interpreta as alterações e aplica atualizações
condicionais no cache.

## 1.2. Atores e responsabilidades

  -----------------------------------------------------------------------
  Elemento                            Responsabilidade
  ----------------------------------- -----------------------------------
  Mock Writers                        Inserem e atualizam veículos e
                                      posições no banco operacional.
                                      Também simulam duplicatas e eventos
                                      fora de ordem.

  PostgreSQL                          Mantém os dados operacionais nas
                                      tabelas `vehicles` e `positions`.

  Debezium                            Captura alterações por meio do WAL
                                      e publica os eventos no Kafka.

  Kafka                               Distribui os eventos CDC em tópicos
                                      independentes por tabela.

  Vehicle Locator Worker              Consome os eventos e mantém a
                                      projeção do estado atual dos
                                      veículos.

  Valkey                              Armazena a última posição e o
                                      estado atual de cada veículo.

  Consumidores do cache               Consultam a projeção para atender
                                      funcionalidades como tracking,
                                      alertas e regras de risco.
  -----------------------------------------------------------------------

## 1.3. Fluxo de dados

1.  Os escritores realizam operações de escrita nas tabelas `vehicles` e
    `positions` do PostgreSQL.
2.  O Debezium captura as alterações por meio da replicação lógica.
3.  Os eventos são publicados em tópicos Kafka independentes,
    correspondentes às tabelas de origem.
4.  O Worker consome os eventos e identifica as alterações por meio dos
    parsers Debezium.
5.  Os deciders determinam se cada alteração deve ser aplicada,
    considerando a ordenação dos eventos.
6.  Os writers atualizam a projeção no Valkey por meio de operações
    condicionais.
7.  Os consumidores consultam o Valkey para obter o estado atual do
    veículo.

**Princípio arquitetural:** o PostgreSQL é a fonte operacional dos
dados, enquanto o Valkey mantém uma projeção otimizada para leitura. O
Worker não realiza consultas diretas ao PostgreSQL.

O ambiente é executado em um cluster Kubernetes local, provisionado com
kind.

O namespace `fleet` concentra os serviços de infraestrutura, a aplicação
e os recursos auxiliares utilizados nos testes E2E.

O diagrama diferencia três grupos:

-   **Infraestrutura:** serviços responsáveis pelo armazenamento

-   **Aplicação:** Worker responsável pelo processamento dos eventos
    CDC.
-   **Validação E2E:** recursos temporários utilizados para preparar

## 2.3. Estratégia de execução e replay

O ambiente E2E utiliza duas projeções independentes para verificar a
consistência do processamento.

  -----------------------------------------------------------------------
  Banco lógico            Responsável             Finalidade
  ----------------------- ----------------------- -----------------------
  Valkey db 0             Worker principal        Mantém a projeção
                                                  utilizada na execução
                                                  normal.

  Valkey db 1             Replay Worker           Mantém uma projeção
                                                  independente,
                                                  reconstruída a partir
                                                  do início do histórico
                                                  disponível no Kafka.
  -----------------------------------------------------------------------

O replay utiliza um grupo de consumidores independente, evitando
interferir nos offsets do Worker principal.

A configuração de replay impede explicitamente que a execução seja
realizada no db 0, protegendo a projeção principal contra sobrescrita.

## 2.5. Considerações operacionais

-   Worker, Replay Worker e Jobs utilizam uma única imagem:
    `vehicle-locator-worker:e2e`.
-   A imagem contém dois binários: `/app/worker` e `/app/mockwriters`.
-   Cada manifest define o comando correspondente ao container.
-   Os Jobs acessam PostgreSQL e Valkey por meio do DNS interno do
    cluster.
-   O Worker utiliza o listener interno do Kafka:
    `kafka-0.kafka.fleet.svc.cluster.local:9092`.
-   O `restart-worker` remove o pod do Deployment `worker` entre
    `seed-a` e `seed-b`. O Kubernetes recria o pod automaticamente.
-   O comando `just forward` é um utilitário local de port-forward e não
    participa da execução do E2E.

# 3. Component

## 3.1. Organização interna do Worker

O Worker é uma aplicação .NET 10 responsável por consumir os eventos CDC
e atualizar a projeção de veículos no Valkey.

Sua organização interna separa o consumo das mensagens, a interpretação
dos eventos, a tomada de decisão e a persistência.

O processamento é dividido em componentes com responsabilidades
específicas:

1.  **Consumers:** mantêm os consumidores independentes para veículos e
    posições.
2.  **ConsumerLoop:** controla polling, processamento, recuperação de
    erros e commit dos offsets.
3.  **Parsers:** convertem os eventos Debezium para os modelos internos
    da aplicação.
4.  **Use Cases:** coordenam o processamento das alterações.
5.  **Deciders:** determinam se uma alteração deve ser aplicada.
6.  **ViewWriters:** persistem as alterações por meio de transações
    condicionais.
7.  **OptimisticWrite:** controla as tentativas de escrita em caso de
    concorrência.

## 3.3. Processamento e garantia de ordenação

O processamento considera que eventos CDC podem chegar duplicados ou
fora de ordem.

Para evitar que uma alteração antiga sobrescreva um estado mais recente,
os deciders utilizam critérios determinísticos de ordenação:

-   Timestamp do evento, expresso em microssegundos.
-   LSN (Log Sequence Number) do PostgreSQL.

A decisão de aplicação é realizada antes da persistência. Dessa forma, a
atualização da projeção respeita a ordem lógica das alterações,
independentemente da ordem em que os eventos são recebidos.

## 3.4. Persistência otimista e concorrência

Os writers utilizam transações condicionais no Valkey para evitar
atualizações inconsistentes.

O mecanismo `OptimisticWrite` executa a operação utilizando condições de
escrita (`AddCondition`) e controla novas tentativas em caso de
conflito.

O comportamento esperado é:

1.  Ler o estado e as versões necessárias.
2.  Avaliar as condições de atualização.
3.  Executar a transação no Valkey.
4.  Em caso de conflito, repetir a operação respeitando o limite de
    cinco tentativas.
5.  Caso as tentativas sejam esgotadas, lançar uma exceção.

Quando o processamento termina em exceção, o offset da mensagem não é
confirmado, permitindo que o `ConsumerLoop` execute o fluxo de
recuperação por meio de `Seek` e tente processar a mensagem novamente.

## 3.5. Tratamento de mensagens inválidas

Os parsers Debezium também são responsáveis por identificar mensagens
que não podem ser convertidas para os modelos internos.

O comportamento definido para mensagens poison é:

-   Registrar o erro em log.
-   Ignorar a mensagem inválida.
-   Confirmar seu offset.

Essa estratégia evita que uma mensagem permanentemente inválida bloqueie
indefinidamente o consumo do tópico.

# 4. Replay e verificação de consistência

## 4.1. Separação de responsabilidades

Os componentes responsáveis pela comparação das projeções não fazem
parte do processamento contínuo do Worker.

Eles são executados exclusivamente pelos Jobs de verificação do E2E.

  -----------------------------------------------------------------------
  Componente                          Responsabilidade
  ----------------------------------- -----------------------------------
  ViewReader                          Lê a projeção armazenada no Valkey.

  ViewComparer                        Compara duas projeções e identifica
                                      divergências.

  assert-view                         Verifica a projeção principal em
                                      relação ao resultado esperado.

  verify-replay                       Compara a projeção principal com a
                                      reconstruída pelo replay.
  -----------------------------------------------------------------------

O Replay Worker executa o mesmo pipeline de processamento da aplicação
principal, utilizando um grupo de consumidores independente e outro
banco lógico do Valkey.

Essa separação permite verificar se a projeção produzida durante a
execução normal corresponde à projeção reconstruída a partir dos eventos
disponíveis no Kafka.
